# Balemoh Foundation Design

**Status:** Approved for specification capture; implementation pending user review of this document.

## Goal

Create the smallest runnable Balemoh foundation: an API-first Go HTTP service with one database-backed health endpoint, embedded self-migrations, SQLite access generated by sqlc, and a clean hexagonal dependency direction.

## Scope

Included:

- Go module `github.com/araihu/balemoh`.
- OpenAPI 3.0 contract for `GET /healthz`.
- `oapi-codegen` generated models and standard `net/http` server interface.
- Application health use case behind an inward-facing port.
- SQLite connection through `database/sql` and a pure-Go SQLite driver.
- `sqlc` generated `Ping` query.
- Embedded `golang-migrate` migrations executed during startup.
- One dummy, reversible bootstrap migration.
- Typed environment configuration with generated documentation.
- Go and macOS `.gitignore` coverage.
- Unit and integration tests for the application, HTTP adapter, and migration startup.

Excluded:

- Business CRUD resources.
- Authentication, authorization, rate limiting, pagination, and background jobs.
- OpenAPI UI, SDK publication, Docker, deployment, CI, and release automation.
- A persistent domain schema beyond the migration bookkeeping needed by the migration library.

## Chosen approach

Use standard `net/http` plus the `std-http-server` oapi-codegen target. This keeps the transport adapter dependency-free while preserving the generated API boundary. A router framework and strict generated server wrapper can be added when real resources create a demonstrated need.

Use `modernc.org/sqlite` as the pure-Go `database/sql` driver. Use `github.com/golang-migrate/migrate/v4` as an imported library, with its `source/iofs` source and SQLite database adapter. The application embeds migration files with `//go:embed`; it never shells out to a migration CLI.

Generated files are committed. Generation commands are deterministic and checked by running `go generate ./...` followed by a clean Git status check.

## Architecture

```text
cmd/balemoh
  composition root: config, SQLite, migrations, sqlc, application, HTTP

internal/application/health
  HealthService
  Pinger port

internal/adapters/http
  oapi-codegen ServerInterface implementation
  request/response translation only

internal/adapters/sqlite
  database/sql connection
  embedded migration runner
  Pinger implementation backed by generated sqlc query

internal/storage/sqlc
  generated Queries and DBTX types

api/openapi.yaml
  contract authority
```

Dependencies point inward. The application package does not import HTTP, SQLite, or generated transport types. The HTTP adapter depends on the application port. The SQLite adapter owns the generated storage package and satisfies the application port. The composition root is the only place that assembles concrete adapters.

The port exists because the requested hexagonal boundary is an architectural contract, even though the foundation has one adapter. It remains intentionally narrow: `Ping(context.Context) error`.

## API contract

`api/openapi.yaml` defines:

- `GET /healthz`.
- `200` response with JSON `{ "status": "ok" }`.
- `503` response with a small JSON error body when the application health dependency fails.
- Stable `operationId` used by generated server code.

The handler calls the application service. It does not open a database or inspect migration state directly. The service calls the `Pinger` port. A successful `sqlc` `SELECT 1` returns the success response; any dependency error maps to the declared `503` response without exposing database details.

## Startup and migrations

Startup sequence:

1. Parse typed configuration before opening external resources.
2. Create the parent directory for the configured local database path.
3. Open SQLite with foreign-key enforcement enabled.
4. Create an `iofs` migration source from the embedded `migrations` filesystem.
5. Run `migrate.Up()` through the imported Go module.
6. Treat `migrate.ErrNoChange` as success; return all other migration errors.
7. Build sqlc queries, application service, generated HTTP handler, and server.
8. Start HTTP server and shut it down on context cancellation.

Migration `000001_bootstrap.up.sql` and its down file execute `SELECT 1;`. The migration is deliberately no-op but proves embedded up/down discovery and version bookkeeping without inventing a domain table. The migration library owns its bookkeeping table.

## Configuration

Use `github.com/caarlos0/env/v11` for typed startup configuration and `github.com/g4s8/envdoc` for generated documentation.

Initial fields:

- `BALEMOH_HTTP_ADDR`, default `:8080`.
- `BALEMOH_DATABASE_PATH`, default `./data/balemoh.db`.

Environment access is confined to the configuration package. Tests inject an environment function rather than mutating process-global environment state. No secret is logged or documented as a value.

## Verification

Required checks:

- `go generate ./...` succeeds and leaves no generated diff.
- `go test ./...` passes.
- `go vet ./...` passes.
- A migration integration test starts against a temporary SQLite database, applies version `1`, restarts without change, and verifies the version remains applied.
- A migration error prevents server construction.
- HTTP tests verify generated routing, `200` success, `503` dependency failure, and response content type.
- Configuration tests cover defaults and malformed values.
- `.gitignore` ignores Go artifacts, local database files, `.env`, and macOS metadata such as `.DS_Store` and `._*`.

## Acceptance boundary

Acceptance means the committed foundation builds, generates, tests, migrates, and serves `/healthz` locally. It does not authorize push, release, deployment, or addition of a business domain.
